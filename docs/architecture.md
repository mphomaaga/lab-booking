# Architecture

Campus lab booking pilot. Design for plan issue #6.

- `docs/spec.md`: the approved spec (spec v3), the source of every requirement.
- `docs/api.yaml`: the API contract (OpenAPI 3.1). Backend and frontend both build to it.
- `docs/data-model.md`: tables, constraints, seed data.
- This file: layout, ownership, configuration, how to run things, cross-cutting rules.

If any of these is wrong or silent on something you need, comment on your issue and stop. Don't guess, and don't edit `docs/` from a build branch.

## Business rule index

"Rule 5.N" in issues and docs means the Nth bullet of spec section 5:

| Rule | Summary |
|---|---|
| 5.1 | Labs open 08:00 to 18:00, Monday to Friday |
| 5.2 | Slots are 1 hour, 10 per lab per open day |
| 5.3 | Lab A, Lab B, Lab C, 30 seats each, kept in the seed |
| 5.4 | Seats are counted, not assigned |
| 5.5 | See and book only today + the next 6 days |
| 5.6 | Max 2 bookings per student per day, across all labs |
| 5.7 | One booking per student per slot; no two bookings at the same time, even in different labs |
| 5.8 | Full slot can't be booked; past slot can't be booked; bookable only until its start time |
| 5.9 | Cancel only your own booking, only before it starts |
| 5.10 | Closure: one lab, one date, today or later, once per lab and date, hides free slots, cancels not-started bookings |
| 5.11 | Public holidays only via closures; no holiday calendar |
| 5.12 | `is_active` takes a lab out of service; set only in seed/DB |
| 5.13 | Any logged-in user can use student features; admin features need `is_admin` |
| 5.14 | JWT lifetime 8 hours, env-configurable, no refresh tokens |
| 5.15 | Store all times in UTC |
| 5.16 | Display times, and interpret opening hours and closure dates, in Africa/Johannesburg |
| 5.17 | Pilot size is 20 students |

## Stack

From spec section 8: Python 3.12 + FastAPI, SQLite via SQLAlchemy 2.x + Alembic, React + Vite + TypeScript, pytest, Playwright (end-to-end, later step), Docker + docker compose, GitHub Actions.

Design choices that the spec leaves to the architect (none of them changes behaviour the spec describes):

| Choice | Why |
|---|---|
| bcrypt (`bcrypt` package) for password hashes | Standard, no extra service |
| PyJWT, HS256 | Spec says JWT; HS256 needs only `JWT_SECRET` |
| `pydantic-settings` for config | Reads env vars with types |
| MSW (Mock Service Worker) for the frontend mock API | Mocks at the network level, so the real API client code is used unchanged when the mock is switched off |
| `react-router-dom` for routing | Four screens |
| Frontend calls the backend directly with CORS (no proxy) | Simplest setup for local and compose |
| Slots created on demand, not pre-generated | The 7-day window rolls daily; no scheduler needed |

## Environment variables

Root `.env` (git-ignored; copy from `.env.example`) is read by docker compose. For local runs, export them or rely on the defaults.

| Variable | Used by | Default | Notes |
|---|---|---|---|
| `JWT_SECRET` | backend | none | Required (spec section 8). Backend refuses to start without it. `.env.example` has a placeholder. Tests set their own |
| `JWT_EXPIRE_MINUTES` | backend | `480` | Token lifetime, 8 hours (rule 5.14) |
| `DATABASE_URL` | backend, alembic, seed | `sqlite:///./lab_booking.db` | Relative to `backend/`. Compose uses `sqlite:////data/lab_booking.db` on a volume |
| `ACCOUNTS_CSV_PATH` | seed | `seed_data/accounts.sample.csv` | Relative to `backend/`. Point at the real Campus Operations CSV, which is never committed |
| `CORS_ORIGINS` | backend | `http://localhost:5173` | Comma-separated list of allowed frontend origins |
| `VITE_API_BASE_URL` | frontend (build time) | `http://localhost:8000` | Backend base URL |
| `VITE_USE_MOCK_API` | frontend (build time) | `false` in `frontend/.env.development` | `true` starts MSW and serves the mock API in the browser, so `npm run dev` works with no backend |

The time zone `Africa/Johannesburg` is a constant in code (`backend/app/core/clock.py`, `frontend/src/lib/time.ts`), not configuration (rule 5.16).

## Running

Local backend (from `backend/`):

```bash
python3.12 -m venv .venv && . .venv/bin/activate
pip install -e ".[dev]"
export JWT_SECRET=dev-secret
alembic upgrade head
python -m app.seed
uvicorn app.main:app --reload            # http://localhost:8000, docs at /docs
pytest                                   # all backend tests, including tests/db/
```

Local frontend (from `frontend/`). `frontend/.env.development` sets `VITE_USE_MOCK_API=false`, so the backend must already be running on port 8000 (the local backend above, or the Docker recipe below). Open the app at `http://localhost:5173`, not `127.0.0.1`: the default `CORS_ORIGINS` allows only `localhost`. To run with no backend, set `VITE_USE_MOCK_API=true` to use the MSW mock.

```bash
npm ci
npm run dev                              # http://localhost:5173
npm run build                            # type-check + production build (what CI runs)
```

Everything in Docker (from the repo root):

```bash
cp .env.example .env                     # then set JWT_SECRET
docker compose up --build                # frontend http://localhost:5173, backend http://localhost:8000
```

The backend container's entrypoint runs `alembic upgrade head`, then `python -m app.seed`, then uvicorn on port 8000. The SQLite file lives on the named volume `db-data` mounted at `/data`. To load the real accounts, mount the CSV into the container and set `ACCOUNTS_CSV_PATH` to its path.

CI (`.github/workflows/ci.yml`) runs on every pull request and on pushes to `main`: job `backend` (Python 3.12, `pip install -e ".[dev]"`, `pytest`) and job `frontend` (Node LTS, `npm ci`, `npm run build`).

## Error format

Every error response, including FastAPI's own validation errors, 404s for unknown routes and unhandled exceptions, has this body:

```json
{ "error": { "code": "slot_full", "message": "This slot is full." } }
```

- `code` is one of `ErrorCode` in `docs/api.yaml`. The frontend switches on `code`, never on `message`.
- `message` is plain English and safe to show to the user.
- `details` appears only on `validation_error` (422) and holds `[{loc, msg}]` from Pydantic.
- Unhandled exceptions return 500 `internal_error` without a stack trace.

Backend: `backend/app/core/errors.py` defines `ApiError(status_code, code, message)`; services raise it and exception handlers in `main.py` render it. Request bodies with unknown fields are rejected (Pydantic `extra="forbid"`), matching `additionalProperties: false` in the contract.

## Time handling

- Database: naive UTC datetimes; `lab_closures.date` is a local date (see `docs/data-model.md`).
- API: instants as UTC `...Z` strings; dates as local `YYYY-MM-DD`.
- Backend: all "now" comes from `app.core.clock.now_utc()` so tests can freeze time. `clock.py` also provides the local-time helpers: today's local date, the local date of a UTC instant, the UTC start/end of a local date, the booking window, and the UTC start times of the ten slots for a local date. Never call `datetime.now()` or `date.today()` elsewhere.
- Frontend: `src/lib/time.ts` formats instants with `Intl.DateTimeFormat(..., { timeZone: 'Africa/Johannesburg' })` and computes "today" in that zone. Never show raw UTC to users.

## Auth

- `POST /auth/login` returns a JWT (claims `sub`, `iat`, `exp`).
- `backend/app/api/deps.py` provides `get_current_user` (401 `not_authenticated`) and `require_admin` (403 `admin_required`). `is_admin` is read from the database on every request, never from the token.
- Frontend stores the token in `localStorage` under `lab-booking.token`. Logout removes it (rule 5.14: no logout endpoint). Any 401 from the API clears the token and sends the user to `/login`.

## Backend structure

- `app/main.py` creates the app, adds CORS, registers the exception handlers and includes one router per module in `app/api/`: `auth.py` (`/auth/login`, `/me`), `labs.py` (`/labs`, `/labs/{lab_id}/slots`), `bookings.py` (`/bookings`, `/bookings/{booking_id}`, `/me/bookings`), `admin_bookings.py` (`/admin/bookings`), `admin_closures.py` (`/admin/labs/{lab_id}/closures`), plus `GET /health`.
- The foundation issue creates every router module as an empty `APIRouter` and includes them all in `main.py`, so endpoint issues only fill in their own module and never touch `main.py`.
- `app/schemas/` holds the Pydantic request/response models for every schema in `docs/api.yaml`. Endpoint issues use them and don't add their own response models.
- `app/services/common.py` holds lookups shared by several areas: active lab or 404, active-booking count for a slot, whether a lab is closed on a local date.
- Tests use an isolated SQLite database per test (created with `Base.metadata.create_all`) and FastAPI's `TestClient`. `backend/tests/conftest.py` provides: `client`, `session`, `frozen_now` (sets the clock), user and admin factories, `auth_headers(user)`, and factories for labs, slots, bookings and closures.

## Frontend structure

- Routes: `/login`, `/book` (Book a slot), `/my-bookings`, `/admin` (Admin bookings, admins only), `/` redirects to `/book`. All routes except `/login` need a token. `/admin` needs `is_admin`; for others it redirects to `/book` and the nav hides it.
- `src/api/types.ts` mirrors `docs/api.yaml` schemas by hand. `src/api/client.ts` has one typed function per operation (`login`, `getMe`, `listLabs`, `getLabSlots`, `createBooking`, `cancelBooking`, `listMyBookings`, `adminListBookings`, `adminCreateClosure`) and throws an `ApiError` carrying `status`, `code`, `message`.
- Screens never call `fetch` directly; they use `client.ts`.
- The mock API (`src/mocks/`) implements every operation in `docs/api.yaml` against in-memory data with the same response shapes and error codes, seeded with the accounts from `backend/seed_data/accounts.sample.csv` and Labs A, B and C.
- Every screen must work at 360 px wide without horizontal scrolling (spec section 7: "All screens must work on a phone").
- Each screen issue edits only its own `src/pages/<Screen>Page.tsx` and its own `src/components/<screen>/` folder. Shared pieces (`Layout`, `api/`, `auth/`, `lib/`, `mocks/`, `App.tsx`, `index.css`) belong to the shell and mock issues; if a screen needs a change there, comment on the issue instead.

## Working rules for build agents

- Branch `<role>/issue-<number>-<short-slug>`, PR into `main`, "Closes #<number>" in the PR.
- Touch only the files listed in your issue. Two issues that run in parallel never share a file; that's what makes parallel work safe.
- Behaviour, status codes and error codes come from `docs/api.yaml`, including the check order written in each endpoint's description.
